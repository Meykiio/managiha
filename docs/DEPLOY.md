# Deploying Managiha

Two pieces: a Supabase project and a static host. Roughly fifteen minutes.

Before you start, note that Managiha has **no backend of its own** — no server, no
API routes, no queue worker. The browser talks to Supabase directly, and the
security model lives in Postgres (row-level security and the write RPCs). So
"deploying" is: point a static host at the built files, and point the app at your
Supabase project.

---

## 1. Supabase project

Create one at [supabase.com](https://supabase.com). The free tier is enough to run
a real shop.

### Apply the schema

Project → **SQL Editor** → New query. Open `supabase/all-in-one.sql`, paste the
whole file, run it **once**.

That file is generated by `npm run db:bundle` from `supabase/migrations/` and is
byte-identical to `supabase/master-schema.sql`, so it cannot drift from the source
of truth. It is **not idempotent** — it assumes a fresh database.

If you prefer to see each step, run the files in `supabase/migrations/` in
filename order instead. That is the same thing with the seams showing, and it is
what to do on a project that already has some of the schema.

Verify:

```sql
select count(*) from public.products;   -- expect 0
```

### Turn off email confirmation, or configure SMTP

**Authentication → Sign In / Providers → Email.**

A fresh project has *Confirm email* **on**, which means signup cannot complete
until the user clicks a link — and Supabase's built-in sender is capped at **2
emails per hour**, which will exhaust itself during your own testing.

For a private or demo instance: turn **Confirm email off**. Signup then works
immediately.

For real users: keep it on, and configure **custom SMTP** under
Authentication → Emails. Do not skip this. With the built-in sender, the third
person to sign up will not receive their confirmation email.

### Redirect URLs — the step everyone forgets

**Authentication → URL Configuration.**

Add your production origin, and the reset path:

```
https://your-domain.com
https://your-domain.com/reset-password
```

Leave `http://localhost:5173/reset-password` in the list for local development.

If you skip this, signup confirmation emails and password reset links point at
`localhost` in production, and nobody can complete either flow.

### Leaked password protection

**Authentication → Policies** (or Settings, depending on the dashboard version) →
enable **Leaked Password Protection**. It checks passwords against HaveIBeenPwned
at signup, costs nothing, and is off by default.

### Storage

The migration creates the private `product-images` bucket and its per-store
policies. Nothing to do — but confirm it exists under **Storage** before you
report an image upload bug.

### Backups

The free tier has **no automatic backups**. Schedule your own:

```bash
supabase db dump --db-url "$DATABASE_URL" -f backup-$(date +%F).sql
```

Put it somewhere that is not the same machine. Losing a shop's sales history
because the database and the backup shared a disk is a bad way to find out.

## 2. Environment

```bash
cp .env.example .env
```

```env
VITE_SUPABASE_URL=https://your-project-ref.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
VITE_SENTRY_DSN=
```

Values are under **Project Settings → API**.

`VITE_SUPABASE_PUBLISHABLE_KEY` is public by design and safe to ship — the prefix
`VITE_` means Vite **inlines it into the JavaScript bundle**, where anyone can read
it. That is fine for the publishable key and catastrophic for the `service_role`
key, which bypasses row-level security entirely.

> **Never put the `service_role` key in a `VITE_` variable, in `.env`, or anywhere
> in this repository.** It belongs in server-side tooling only.

`VITE_SENTRY_DSN` is optional. Left empty, Sentry is not initialised and only the
in-app error boundary is active.

## 3. Build and host

```bash
npm install
npm run build      # typecheck + vite build → dist/
```

`dist/` is a static directory. Any host will serve it. `vercel.json` is included
and sets:

- **SPA rewrites**, so a deep link like `/carnet/<id>` serves `index.html` instead
  of 404ing. Anything under `/assets/` is excluded, because those are
  content-hashed and immutable.
- **A Content Security Policy.** `script-src` is `'self'` plus one SHA-256 hash —
  the inline theme bootstrap in `index.html` that applies the theme before first
  paint so there is no flash of the wrong colours.
  **If you edit that inline script, the hash changes and you must update
  `vercel.json`**, or the page will render with the theme script blocked.
- `connect-src` allows `https://*.supabase.co`, `wss://*.supabase.co` and Sentry.
- `camera=(self)` is required: the barcode scanner uses it. It is not looseness —
  a wrong value here silently breaks scanning.

### Vercel

```bash
npx vercel          # preview
npx vercel --prod   # production
```

Set the two environment variables in the Vercel project settings, then redeploy —
they are baked in at build time, so changing them requires a rebuild, not a
restart.

Then add your production domain to Supabase's redirect allow-list (step 1).

## 4. After deploying

- Sign up once and confirm you land on the dashboard.
- Open **Products → Add**, save something, and check the stock movement appears in
  **Inventory → History**.
- Take a sale in **Scanner** and confirm it appears in **Reports → Ventes**.
- Open the app on a phone over HTTPS. **The barcode scanner needs a secure
  context** — it works on `https://` and on `localhost`, and will silently refuse
  to start on a plain `http://` LAN address.
- Switch to Arabic and check the layout mirrors.
- Run the SQL suites once against the production project to confirm the schema is
  complete. They clean up after themselves and only touch their own test rows.
- Confirm the Resend/confirmation email actually arrives, if you kept email
  confirmation on.

### Optional: a public demo store

`supabase/seed-demo.sql` builds a populated store on a `demo@managiha.app` account:
twelve products, three suppliers, three customers with balances, and a history of
sales.

Sign up once with that address in the app, then run the file in the SQL Editor. It
is safe to re-run — it wipes only that account's own rows first.

If you publish the demo credentials in your README, understand that they are
public: anyone can log in and change the demo data. That is the point of a demo,
but do not put anything real in that account.

## Self-hosting notes

- **Nothing stateful lives in the built files.** The app is static and the data is
  in Supabase, so a redeploy is never a migration.
- **The write RPCs are the security boundary, not the host.** A compromised static
  host can serve tampered JavaScript, but cannot do more through Supabase than the
  logged-in user could — RLS and the guard triggers are in the database.
- **PostgREST caches the schema.** After a migration that changes a function
  signature, run `notify pgrst, 'reload schema';` and restart the API from the
  Supabase dashboard. A stale cache presents as a confusing
  "function does not exist" error on a function that plainly does.
- **Region.** Supabase projects sit in a specific region, and Algerian data
  protection law has a position on cross-border transfer. Read
  [LEGAL.md](LEGAL.md) before choosing one for real customers.
