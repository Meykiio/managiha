مانجيهة يعوّض الدفتر الذي خلف الطاولة. اعرف ما لديك على الرف، وكم يساوي، وما
سيؤول، ومن ما زال مدينًا لك، وما ربحته فعلًا هذا الشهر — بالفرنسية أو الإنجليزية
أو العربية.

مصمَّم لصاحب محلّ واقف على قدميه، يحمل هاتفًا، وزبون ينتظر.

## لماذا مانجيهة

تجارة التجزئة في الجزائر يقوم بها في الغالب محلّات صغيرة يديرها أصحابها. وهناك
أمران يخرّبان العمل الورقي، وكلاهما يخرّبه في صمت:

1. **المخزون.** ما نقص، وما نفد، وما قارب انتهاء صلاحيته، وكم يساوي الرف فعلًا.
   الدفتر يقول «5 أكياس فرينة» وكان آخر تحديث له قبل ثمانية أيام.
2. **الكارني.** الزبائن يشترون بالدين ويسدّدون لاحقًا. الدفتر يكتب «ديّ 3500» بلا
   تاريخ، وبلا مجموع جارٍ، وبلا طريقة لمعرفة «كم يدين أحمد؟» دون قراءة كل صفحة.

الأدوات الموجودة إمّا مصمّمة للمحاسبين، أو محجوبة خلف اشتراك، أو موجّهة للمساحات
الكبرى. مانجيهة بحجم العمل الحقيقي: محلّ واحد، صاحب واحد، وهاتف.

**مانجيهة** — من الفعل *gérer* أي «يُدير».

## ما الذي يفعله

- **البيع على الطاولة** — سلّة بملء الشاشة، امسح الباركود *أو* اكتب الاسم، دفع
  نقدًا أو بالدين، حساب الباقي، وإيصال لا يظهر إلا بعد تأكيد الخادم. ويمكن إنشاء
  منتج بلا باركود أثناء البيع دون مغادرة السلّة.
- **معرفة المخزون** — استلام مع تواريخ انتهاء الصلاحية وأرقام الدفعات، وتسويات
  بسبب إلزامي (جرد، تلف، سرقة، إرجاع، تصحيح)، و**جلسة جرد الرفوف** التي تمشي في
  المحل بدل فتح أربعين نافذة.
- **تجنّب خسارة انتهاء الصلاحية** — تُتابع الدفعات بترتيب FEFO (الأقرب انتهاءً
  يُصرف أولًا)، وتعرض لوحة المتابعة ما سيؤول وقيمته، ويمكن شطب أي دفعة بإجراء واحد.
- **إدارة الكارني** — الأرصدة لكل زبون، قيود الدين والتسديد، سجلّ جارٍ، و**تذكير
  واتساب معبّأ مسبقًا** يفتح في واتساب صاحب المحل نفسه. بلا واجهة برمجية، وبلا
  توثيق تجاري، وبلا حساب.
- **معرفة الأرباح** — الإيرادات والكميات والهامش المقدّر على مدى 7 أو 30 أو 90
  يومًا، والمنتجات الأكثر بيعًا، والمنتجات الراكدة، و**قائمة إعادة الطلب مجموعة
  حسب المورّد** يمكن إرسالها كطلبية على واتساب.
- **رؤية الهامش أثناء تحديد الأسعار**، مع تحذير قبل البيع بأقل من سعر التكلفة.
- كل تقرير يُصدَّر إلى CSV بصيغة يفتحها Excel مباشرة.

العربية مدعومة بالكامل من اليمين إلى اليسار. واجهتان: داكنة وفاتحة. والعملة
مثبّتة على الدينار الجزائري.

### ما ليس مانجيهة

مانجيهة **أداة إدارة خلفية، وليست نقطة بيع**. يسجّل ما بعته لتعرف ما لديك وما
ربحت، لكنه **لا** يصدر فواتير جبائية (المرسوم التنفيذي 05-468)، ولا يعالج الدفع
بالبطاقة، ولا يطبع تذاكر جبائية، ولا يُغلق صندوقًا.

وهذا اختيار مقصود. ابتداءً من **1 جانفي 2027**، تُلزَم المؤسسات الجزائرية التي
تستعمل «برنامج تسيير أو نظام صندوق» بحيازة شهادة تُثبت عدم قابليّة التغيير
والأمان والحفظ والأرشفة لبياناتها. وهذا الالتزام يقع على عاتق صاحب المحل. والبقاء
خارج صنف الصندوق يعني ألّا ترث التزامًا لا يستطيع هذا البرنامج أن يشهد له — وأن
تستعمل مانجيهة إلى جانب أي نظام جبائي تعتمده أصلًا.

## التقنيات المستعملة

| الطبقة | الاختيار |
|---|---|
| الواجهة | React 18، TypeScript (صارم)، Vite، Tailwind CSS، react-router-dom |
| عناصر الواجهة | مجموعة صغيرة داخلية (`components/ui/`) مبنية على رموز التصميم — بلا مكتبة جاهزة |
| البيانات | Supabase: Postgres + المصادقة (PKCE) + التخزين، مع أمن على مستوى الصفوف |
| الأمان | RLS على الجداول الأحد عشر، دوال كتابة `SECURITY DEFINER`، مُشغّلات حماية، مفاتيح منع التكرار |
| تعدد اللغات | الفرنسية / الإنجليزية / العربية، مع RTL، واكتمال المفاتيح مضمون بالأنواع |
| دون اتصال | طابور كتابة دائم في IndexedDB لقيود المخزون والكارني (وليس للبيع) |
| الأيقونات | lucide-react |
| الاختبارات | Vitest + Testing Library، وPlaywright + axe، وستّ مجموعات SQL |
| الأخطاء | Sentry (اختياري — معطّل ما لم يُضبط مفتاح) |

اعتماديات التشغيل: React وreact-router وSupabase وlucide-react وclsx
وhtml5-qrcode وSentry. هذه هي القائمة كاملة، وهي قصيرة عن قصد — لأن التطبيق يعمل
على هاتف أندرويد رخيص واتصال ضعيف.

## البدء

### المتطلبات

| الأداة | لماذا |
|---|---|
| **Git** | لاستنساخ المستودع |
| **Node.js 20+** | لبناء التطبيق وتشغيله (يُنصح بـ 22 LTS — فالإصدار 20 انتهى دعمه) |
| **npm** | يأتي مع Node |
| **مشروع Supabase** | الخطة المجانية تكفي — [supabase.com](https://supabase.com) |

لا حاجة إلى Docker. مانجيهة يعتمد على مشروع Supabase مستضاف، ومجموعات اختبار SQL
تعمل عليه مباشرة.

### بدء سريع

```bash
# 1. استنساخ
git clone https://github.com/Meykiio/managiha.git
cd managiha

# 2. التثبيت
npm install

# 3. ملف البيئة
#    على macOS / Linux / Git Bash:
cp .env.example .env
#    على Windows PowerShell:
#    Copy-Item .env.example .env
#    ثم الصق Project URL والمفتاح العام في .env

# 4. إنشاء قاعدة البيانات، مرّة واحدة
#    لوحة Supabase -> SQL Editor -> New query
#    الصق كامل محتوى supabase/all-in-one.sql ثم Run.

# 5. التشغيل
npm run dev
# افتح http://localhost:5173
```

ثم **سجّل بأي بريد واسم محلّ** — يُنشئ مُشغّل قاعدة البيانات صفّي `stores`
و`profiles` تلقائيًا، فلا توجد خطوة إعداد.

قبل التسجيل، أوقف خيار *Confirm email* في
**Authentication → Sign In / Providers → Email**. المشروع الجديد يفعّله افتراضيًا،
وهو يمنع إتمام التسجيل حتى النقر على الرابط، كما أنّ مُرسِل البريد المدمج محدود
ببريدين في الساعة — وستستنفده أثناء تجربتك أنت. التفاصيل الكاملة، بما فيها ما
يُفعل للمستخدمين الحقيقيين، في [docs/DEPLOY.md](docs/DEPLOY.md).

> ملف `supabase/all-in-one.sql` مُولَّد من `supabase/migrations/` عبر
> `npm run db:bundle`، وهو مطابق لـ `supabase/master-schema.sql`. وهو **غير
> قابل للتشغيل مرّتين** — شغّله على قاعدة بيانات جديدة فقط.

### إعداد بنقرة واحدة (لمن لا يعرف البرمجة)

انسخ الأمر التالي والصقه في أي مساعد برمجة ذكاء اصطناعي — Claude Code أو Cursor
أو opencode أو Codex أو Gemini CLI أو Windsurf — ودعه يفعل كل شيء. يكتشف نظام
تشغيلك، ويثبّت ما ينقص، وينشئ ملف البيئة، ويوصلك إلى مانجيهة يعمل مع حساب جاهز.

### أمر الإعداد بنقرة واحدة — الصقه في مساعدك الذكي

```
أنت تُعِدّ «مانجيهة»، تطبيق مفتوح المصدر لإدارة المخزون ودفتر ديون الزبائن
للمحلّات الصغيرة (React + TypeScript + Vite + Supabase). المستخدم ليس مبرمجًا.
اعمل باستقلالية، وتحقق من كل خطوة، واشرح كل خطوة في جملة واحدة بسيطة. لا تتجاوز
أي تحقق فاشل: شخّص السبب الجذري، وأصلحه، ثم أعد التشغيل قبل المتابعة. وصرّح بصدق
إذا تعذّر إنجاز شيء بدلًا من الارتجال.

الهدف: تشغيل مانجيهة على http://localhost:5173، متصلًا بمشروع Supabase مطبَّق
عليه المخطط، مع حساب أول يستطيع تسجيل الدخول والوصول إلى لوحة المتابعة.

سياق مهم
- مانجيهة ليس له خادم خاص به. المتصفح يتصل بـ Supabase مباشرة. لذا لا يوجد سوى
  أمرين لإعدادهما: Node ومشروع Supabase.
- Docker غير مطلوب ويجب ألّا يُستعمل. لا توجد حزمة Supabase محلية.
- مُرسِل البريد المدمج في Supabase يسمح ببريدين في الساعة فقط، لذا يجب إيقاف
  تأكيد البريد أثناء الإعداد.

اسأل سؤالًا واحدًا أولًا قبل تثبيت أي شيء:
«هل لديك مشروع Supabase بالفعل، أم أدلّك على إنشاء مشروع مجاني؟»
ثم اتبع المسار الذي اختاره. انتظر الجواب.

الخطوات:

0. اكتشف نظام التشغيل أولًا. حدّد النظام (Windows أو macOS أو Linux) ومعمارية
   المعالج، وعلى Windows حدّد أيضًا هل أنت في PowerShell أم cmd أم Git Bash،
   واستعمل الصيغة الصحيحة لكل منها. واذكر النظام الذي اكتشفته.

1. تحقق من المتطلبات. افحص كل أداة، وثبّت ما ينقص بالطريقة المناسبة للنظام.
   واذكر بدقة ما ثبّتته، وهل يلزم إعادة تشغيل.
   - Git: `git --version`
     Windows: winget install Git.Git
     macOS:   brew install git   (أو استعمل المدمج)
     Linux:   apt install git    (أو dnf install git)
   - Node.js 20+: `node -v`
     Windows: winget install OpenJS.NodeJS.LTS
     macOS:   brew install node
     Linux:   apt install nodejs npm   (أو استعمل nvm)
   - npm: `npm -v`   (يأتي مع Node)
   إذا كان Node أقدم من 20، فحدّثه قبل المتابعة.

2. الاستنساخ. إن لم تكن المجلد الحالي هو المشروع:
   git clone https://github.com/Meykiio/managiha.git
   cd managiha

3. تثبيت الاعتماديات. شغّل `npm install`. وصرّح بصدق إن فشل، وأصلح السبب الجذري.

--- إعداد Supabase ---

4. الحصول على المشروع. إن كان لديه مشروع، اطلب منه فتحه والذهاب إلى
   Project Settings -> API. تحتاج قيمتين:
     - Project URL          (https://<ref>.supabase.co)
     - المفتاح العام publishable / anon
   ووضّح بدقة: المفتاح العام عام وآمن في التطبيق. أما مفتاح service_role فليس
   كذلك — فهو يتجاوز كل الحماية — ويجب ألّا يُستعمل هنا ولا يُلصق في أي ملف في
   هذا المشروع. وإن لم يجد القيم، دلّه على الصفحة الصحيحة.
   وإن لم يكن لديه مشروع: اطلب منه إنشاء واحد على supabase.com بالخطة المجانية
   (واختيار منطقة قريبة منه)، ثم العودة إلى صفحة API.

5. إيقاف تأكيد البريد. اطلب منه الذهاب إلى
   Authentication -> Sign In / Providers -> Email وإيقاف "Confirm email" ثم
   الحفظ. المشروع الجديد يفعّله، وهو يمنع التسجيل كليًا ويستهلك حصة البريد
   المجانية. هذه الخطوة إلزامية لا اختيارية.

6. تطبيق المخطط، مرّة واحدة. لوحة التحكم -> SQL Editor -> New query. اقرأ
   `supabase/all-in-one.sql` والصق كامل محتواه، ثم Run. يُنشئ كل الجداول
   وسياسات أمن الصفوف ودوال الكتابة ومُشغّلات الحماية وحاوية التخزين. شغّله مرّة
   واحدة فقط على مشروع جديد.
   تحقق من النتيجة:
     select count(*) from public.products;    -- يجب أن يُرجع 0
   وإن ظهر خطأ، اقرأ رسالته: السبب الأكثر شيوعًا هو تشغيله مرتين.

7. أنشئ ملف `.env` في جذر المشروع (لا ترفعه إلى Git أبدًا):
     VITE_SUPABASE_URL=<Project URL>
     VITE_SUPABASE_PUBLISHABLE_KEY=<المفتاح العام>
     VITE_SENTRY_DSN=
   طابق `.env.example` تمامًا. ولا تخترع متغيرات إضافية.

--- الإنهاء ---

8. تشغيل التطبيق. شغّل `npm run dev` في الخلفية. وتأكد من أن
   http://localhost:5173 يُحمَّل بلا أخطاء في الطرفية أو وحدة التحكم.
   وإن كان المنفذ 5173 مشغولًا، فاذكر ذلك واستعمل منفذًا آخر بدل الفشل الصامت.

9. فحص الأنواع. شغّل `npm run typecheck`. وصرّح بالنتيجة بصدق. (استعمل أمر npm،
   وليس `tsc --noEmit` مباشرة — لأن ملف tsconfig الجذري يستعمل مراجع مشاريع،
   فالاستدعاء المباشر لا يفحص أي ملف وينجح دائمًا.)

10. أنشئ الحساب الأول في التطبيق: أي بريد، وأي اسم محلّ. وتأكد من وصوله إلى لوحة
    المتابعة. وإن لم يفعل، فالسبب المعتاد بالترتيب: تأكيد البريد ما زال مفعّلًا
    (الخطوة 5)، أو المخطط غير مطبَّق (الخطوة 6)، أو قيم خاطئة في .env (الخطوة 7).
    شخّص ولا تخمّن.

11. بيانات تجريبية اختيارية. إن أراد المستخدم محلًّا معبّأ بدل محلّ فارغ، اطلب منه
    التسجيل مرّة واحدة بالعنوان `demo@managiha.app`، ثم تشغيل
    `supabase/seed-demo.sql` في SQL Editor. يبني اثني عشر منتجًا وثلاثة مورّدين
    وثلاثة زبائن بأرصدة وسجلّ بيع، وبعض الرفوف الفارغة أو الناقصة.

12. التقرير النهائي. اطبع ملخّصًا واضحًا:
    - ما يعمل وأين (رابط التطبيق، ورابط لوحة Supabase)
    - أوامر الاستعمال اليومي: `npm run dev` للتشغيل، وCtrl+C للإيقاف
    - كيفية تشغيل الفحوص: `npm run gate` (lint، types، 134 اختبارًا، build)
      و`npm run gate:all` (يضيف اختبارات المتصفح وknip)
    - ما هو **غير** مفعّل عن قصد ولماذا: الفاتورة الجبائية وميزات صندوق النقد خارج
      نطاق المشروع تصميمًا؛ وSentry معطّل لغياب المفتاح
    - أي مشكلة لم تُحلّ، مع نصّ رسالة الخطأ كما هي

قواعد صارمة
- لا ترفع أي سرّ إلى Git، ولا تكتب مفتاح service_role في .env أو أي ملف في هذا
  المستودع.
- لا تُضف أو تحذف أو تحدّث أي اعتمادية. استعمل ما في package.json.
- لا تعدّل شيئًا تحت supabase/ إلا بتشغيل الملفات الموجودة.
- Docker غير مطلوب ولا مرغوب.
- إن تعذّرت خطوة، توقف واشرح بالضبط ما ينقص. لا ترتجل حلًّا يتظاهر بالنجاح.
```

### محلّ تجريبي

يبني الملف `supabase/seed-demo.sql` محلًّا معبّأ على حساب `demo@managiha.app`:
اثنا عشر منتجًا في خمس فئات، وثلاثة مورّدين، وثلاثة زبائن بأرصدة، وسجلّ بيع حقيقي
مُسجَّل عبر الدوال نفسها التي يستعملها التطبيق، وأربعة منتجات متروكة عن قصد ناقصة
أو منتهية ليكون للتنبيهات ما تعرضه.

سجّل مرّة واحدة بذلك العنوان في التطبيق، ثم شغّل الملف في SQL Editor. وهو آمن
لإعادة التشغيل — يمسح صفوف ذلك الحساب وحده أولًا.

هناك نسخة مستضافة على **<https://managiha.vercel.app/>**. وبيانات دخولها
`demo@managiha.app` / `Managiha2026` وهي تعمل — فالنشر يشير إلى المشروع الذي
زُرع فيه ذلك المحلّ.

> أي بيانات دخول منشورة هي عامة بطبيعتها. اعتبر ذلك الحساب محلًّا تجريبيًا، ولا
> تضع فيه بيانات محلّ حقيقي.

## النشر

مانجيهة بناء ثابت بلا خادم، فالنشر هو: استضف الملفات، ووجّه التطبيق إلى مشروعك.

```bash
npm run build      # فحص الأنواع + vite build -> dist/
```

يحتوي `vercel.json` على إعادة توجيه SPA، وسياسة أمان المحتوى، وترويسات التخزين
المؤقت. والتعليمات الكاملة — بما فيها روابط التوجيه في Supabase التي ينساها
الجميع، والبريد المخصص، وحماية كلمات المرور المسرّبة، والنسخ الاحتياطي — في
**[docs/DEPLOY.md](docs/DEPLOY.md)**.

## التحقق

البوابة الكاملة، بالترتيب:

```bash
npm run gate        # eslint + tsc + 134 اختبارًا + بناء الإنتاج
npm run gate:all    # ما سبق + 20 اختبار متصفح/axe + knip
```

و`gate:all` هو ما يُشغَّل قبل فتح طلب دمج.

تؤكد مجموعة اختبارات المتصفح **خلوّ كل صفحة عامة من مخالفات axe، في الواجهتين
وفي RTL** — وهذا خلل لا تراه اختبارات الوحدة. والمجموعة كاملة خضراء: 134 اختبارًا
عبر 18 ملفًا، و20 اختبارًا شاملًا، وبناء إنتاج نظيف، وknip بلا ملفات أو تصديرات
غير مستعملة.

### مجموعات اختبار SQL

ستّ مجموعات في `supabase/tests/`، **96 تأكيدًا**، وكلها تنظّف نفسها. تعمل على
PostgreSQL حقيقي (17.11 عند آخر تحقق) داخل SQL Editor:

| المجموعة | التأكيدات | ما تُثبته |
|---|---|---|
| `rls_rpc_tests.sql` | 21 | عزل المخازن، ومُشغّلات الحماية، وسجلّ لا يُعدَّل |
| `checkout_rpc_tests.sql` | 16 | البيع، وتوزيع FEFO، ومنع التكرار |
| `product_lots_tests.sql` | 17 | حساب الدفعات، وثبات مجموعها |
| `trends_rpc_tests.sql` | 11 | تجميع لوحة المتابعة |
| `legal_rpc_tests.sql` | 12 | تصدير البيانات وإخفاء الهوية |
| `insights_rpc_tests.sql` | 19 | المبيعات والهامش والركود وإعادة الطلب |

وهي يدوية لأن Docker رُفض. وهي أيضًا ما كشف أخطاء لم تكشفها أربع مراحل من مراجعة
الكود — من بينها بيع مسجَّل من شاشة الجرد بلا سعر، فلم يُدرّ أي ربح. اعتبرها بوابة
حقيقية لا إجراءً شكليًا.
